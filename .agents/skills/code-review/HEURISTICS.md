# Review heuristics

How to reach a finding, how to turn it into a suggestion, and how to word it. Read by the Standards sub-agent (Finding) and the lead (all three). Every item is a judgement call; the smell baseline and the repo's documented standards still decide what counts as a violation.

## Finding

- **Premise before mechanism.** State the problem the change solves, then ask whether the fix sits at the right layer and whether the diff's own justification is true. Verify "this works because the data is stored/served this way" against the actual schema and routes; a neighbour that looks alike in the component layer can have a different storage story underneath. Mechanism checks (dead branches, casts, scope bleed, security-sensitive surface) come naturally; the premise question is the one that goes unasked, and it is the one that most often makes the rest moot (a client-side fallback masking a data-completeness gap).
- **Does this state ever happen?** For each guard or defensive branch, trace the real constraints: FKs, NOT NULL, UNIQUE, the type, the call sites. A guard for an unreachable state misleads, since a reader infers a path exists. Keep one only when platform mechanics force it (a `DELETE` branch where `NEW` is genuinely unset). Take the code's own comment as a claim to check, not a reason to stop (a dedup filter "because the crawler can leave duplicates" that two composed UNIQUE constraints already foreclosed). List the claims before reading the mechanism; read inline, a claim passes as context and gets quoted into a finding instead of opened.
- **Layer of responsibility.** For every invariant a change relies on or defends, name the layer that owns it and verify there. When a bug spans two layers (a stored aggregate and a computed display value drifting apart), weigh the fix at the shared root against the fix at the symptom, and surface both so the human picks depth versus safety.
- **Trace every call site** of a changed shared function; the effect differs per caller (safe here, cosmetic there, broken elsewhere). One leading sort key added to a shared ordering helper: three callers fine, one list could show an item that no longer met the list's own filter. Depth follows the kind of change: a call-site edit needs its callers; an *extraction* (a new helper, a shared SQL fragment, a pulled-out primitive) needs its siblings, because the copies it didn't absorb are the finding. A security finding on one construction needs every copy of that construction, since a per-site fix leaves the rest.
- **Answer the question asked.** "No index touches it and the rows are bounded" answers a performance question; the question was correctness. A satisfying answer to the wrong question is not a reason to end the trace.
- **Convention, not instance.** On an inconsistent fix, ask whether a convention exists for that class of change. None: the finding is the gap, and the signal is repeated, independently drifting literals for the same idea. Exists and violated: ask oversight or deliberate exception. Deliberately absent: surface the choice.
- **Declarative data: trace the consumer.** A config list reads as fine until you find who depends on its order and who writes it. Ask what downstream computes on the empty set; that is where config hides its consequences (an empty field set hashing to a constant, which a UNIQUE constraint then turns into silently dropped rows).
- **Absence.** The hardest thing to see and the most valuable to flag in a schema or taxonomy change: for each declared entity, ask what its siblings carry that it lacks.
- **Transcribed tests.** An assertion that reads like observed output (`values.at(-1) === '20 GB'`) pins a defect as expected behaviour. Target the framing: assert the invariant.
- **Verbose inline justification** is a weak signal that the decision underneath was made fast and not scrutinised. Look harder at that decision, on top of the usual checks.
- **Read the code as a stranger's story.** For every error message, name and log line in the diff, ask whether the surrounding code established the fact it states. One that knows more than its context is a layer leak, and the leak is the finding, not the redundancy it shows up as (a generic handler whose error text names the one kind of request it really serves).
- **Bundled product decisions.** A user-facing feature quietly disabled as a byproduct (a nav link made non-interactive) is a product decision inside a code change. Call it out as such.
- **A preview is a claim about a later state.** A confirmation or preview UI asserts what will happen; trace to the real producer and check they agree. Where the real behaviour differs from what a human reads off the picture (a crop, a resize, a delay), the UI has to say so. The testing twin: assert the invariant a human would miss, not the one they'd notice.
- **Rendered layout is out of reach.** A diff review proves static facts: contrast via the variable chain, dead conditionals, unreachable states. Spacing that emerges at render is invisible to it. Itemise which changes only show visually (gap/padding/margin, new wrappers, alignment classes) as a "worth eyeballing" list, so the human's visual pass lands where it matters. The same holds for a value that must agree with a system outside the repo (a storage key layout, a dashboard setting): the diff can show it is self-consistent, not that it is right. List each beside the render-only list as "worth checking against <system>".

## Suggesting

- **Flag from the rule, suggest from the intent.** A standards flag (comment length, reference direction, a value in the wrong layer) says *where*; the suggestion comes from asking what the author was telling the reader and which layer owns that fact. Write the sentence that belongs in each place. Cut only when the intent has no home: a comment that echoes the request rather than the code ("larger than a card's… 13px under 20px") is the usual case.

## Reporting

- **Surface half-formed doubts.** "Intentional, or a side effect?" is a question only the human answers. Finishing the trace is cheap and sometimes turns "maybe confusing" into a provable defect; ask rather than pick the charitable reading.
- **Blast radius, precisely.** A tiebreak decides only exact ties; a key checked first decides most rows. Say which one a sort change is; the two have very different sizes.
- **Asymmetric cost.** "Adding it later recomputes every stored hash" moves a question from opinion to scheduling, which is what gets it decided.
- **A question is not authorisation.** "What's your recommended fix?" is answered in the finding. Edit code on an instruction ("apply that"), and when unsure, comment and ask.
